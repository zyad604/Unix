# Architecture

Unix is a Blender add-on. It has no server of its own and no account system. The model runs through the user's own Claude CLI; everything else runs inside Blender.

## The loop

```
 chat panel ──send──▶ Engine ──spawns──▶ claude CLI (-p, stream-json)
     ▲                  │                      │
     │              tick (timer)               │ MCP over HTTP, 127.0.0.1, bearer token
     │                  ▼                      ▼
     └──events── event queue ◀── reader   McpServer (worker threads)
                                                │ submit(fn)
                                                ▼
                                      MainThreadDispatcher ──pump──▶ tool runs on Blender's main thread
```

1. The user sends a message. `core.Engine.send` writes the system prompt and an MCP config file, then starts `claude -p` with built-in tools disabled and user/project settings ignored.
2. The CLI connects to `bridge.mcp_server.McpServer` inside Blender and sees our tools as native tools. It is the agent loop: it calls tools, reads results (text and images), and decides what to do next.
3. A tool call arrives on an HTTP worker thread. `tools.registry.Registry.call` validates the arguments and hands the function to `bridge.main_thread.MainThreadDispatcher`, which blocks the worker until Blender's main thread runs it.
4. A persistent `bpy.app.timers` callback (`__init__._tick`) pumps the dispatcher and drains the CLI's event stream into the chat state, then redraws the panel.
5. The CLI's session id is kept, and the next message resumes it, so the conversation has memory without the add-on storing prompts.

## Why it is built this way

| Decision | Reason |
|---|---|
| Tools are exposed over MCP, not parsed out of model text | Native tool calling is reliable, supports parallel calls, and lets a tool return an image the model actually sees. |
| The Claude CLI is the agent loop | It already handles context, retries and streaming. The add-on stays small and has nothing to keep in sync with a model API. |
| CLI built-in tools are off (`--tools ""`) and settings are ignored | The model can only act through Blender tools. It cannot edit files or run shell commands on the machine. |
| Loopback bind, random port, bearer token | Another local process cannot drive Blender through the bridge. |
| One undo push before the first change and one at turn end | A single Ctrl+Z reverts the whole turn. |
| A `.blend` snapshot before the first change of a turn | A hard fallback when undo is not enough. Newest 20 are kept. |
| Chat state lives in Python, not on the Scene | Undo must rewind the scene, not the conversation. |
| `run_python` has a guard, a deadline and a scene diff | The guard refuses destructive calls, the deadline stops runaway loops, and the diff tells the model what really changed. |
| `look` returns renders to the model | Numbers do not show bad proportions or floating parts. Seeing the result is the main quality lever. |
| `api_lookup` reads RNA from the running Blender | It removes guessed operator and property names, the most common cause of failed scripts. |
| Every message carries a context block | Selection, mode and the user's manual changes since the last turn reach the model without a tool call. |
| Chats are JSON sidecar files written at every turn end | History survives a crash and is never rewound by undo. |
| Restore opens a copy of the snapshot | The user's file on disk is never written without an explicit "save back". |
| Tools return receipts | `set_material` reports what drives the surface and who shares the material; `run_python` reports the object diff and triangle count. |
| Asset downloads are allowlisted, size-capped, md5-checked and cached | The model can use real HDRIs and scanned materials without free network access. |
| Two interchangeable agent loops | The Claude CLI and the Codex CLI both speak MCP, so either can drive the same tools; the engine only sees one event format. |
| Image generation goes through the Codex CLI with its shell and tools disabled | OpenAI images with the user's ChatGPT login and no API key; the subprocess can do nothing but generate. |
| The island is drawn with `gpu` and `blf` and driven by one always-on modal operator | Panel widgets cannot do rounded cards, gradients, image previews or a text box inside the viewport. The operator handles clicks, the wheel and typing, and passes every other event through. |
| Engines are found by discovery, not by an engine-side plugin | Running editors expose their project on the command line and every engine keeps a recent-project list; writing the file into the folder the engine watches is enough for Unity, Unreal and Godot to import it. |
| Unreal gets a live link through its own Python remote execution, not a plugin of ours (`tools/unreal.py`, `bridge/unreal_link.py`, `bridge/unreal_build.py`) | Writing an FBX into Content/Unix only made Unreal offer an import: nothing was placed, materials arrived as stubs and lights were lost, so a map could not travel. The Python Script Plugin that ships with the engine (4.26+) already runs Python sent from another program when the project has remote execution on: UDP multicast discovery (group 239.0.0.1:6766, `ping`/`pong` carrying the project folder), then a TCP channel that the editor opens back to us, one JSON `command` and one `command_result` each. Read from Epic's C++: the editor parses every chunk it receives as a whole message, so the command stays one line (`runpy` of the builder) and everything else travels as files. Blender exports each distinct mesh once at its own origin (linked duplicates and collection instances share it) with its slots renamed `UnixSlot0..n` so Unreal's slots are found by name, materials as numbers and pictures for one master material per blend mode that Unix owns (node-made looks baked with `roblox_surface.Baked`, normal maps flipped to DirectX), lights on Blender's own scale (a sun of strength S is S lux, P watts are P/4pi candela, a glow of strength E an emissive E: a white surface under one unit of light reads the same at Blender's exposure 0 and Unreal's exposure 1; the physical 683 lm/W were tried first and burnt a default level out to white, its auto exposure cannot reach that far), the camera with its horizontal field of view, and every transform converted (x, -y, z) x 100 with rotations F R F (F R A for lights and cameras, which look down -Z in Blender and +X in Unreal). The editor imports, makes instances, and spawns actors in the open level, tagged `UnixAsset:<name>` so a resend replaces them; content goes under the open level's mount point (`/UGC123/Unix/...` for a level in a mod plugin, so the mod packages it). When no editor answers, the send still writes the FBX and switches the link on in the project's own files (the two plugins in the .uproject, `bRemoteExecution=True` in DefaultEngine.ini, each backed up, only that text changed), because the user asked for that instead of a setting to tick; the editor reads it at its next start. |
| Engine exports use a stable file name and a temporary base-centre pivot | Re-sending overwrites the file so the engine re-imports in place; the pivot move is applied only for the export and the scene is restored. |
| A tool may return `Pending(poll)` instead of a result | A bake or a reply from another program takes minutes. Blocking the main thread for that long makes Windows grey the window out as "Not Responding". The registry sleeps on the worker thread and calls `poll` on the main thread until it returns the result. |
| Long main-thread work runs in slices (`bridge/main_thread.py`): a tool or the end of a turn written as a generator yields where it may pause | On a big scene (1,200 objects) the check after a turn held the main thread for 7 to 11 s, `check_scene` for 7 to 10 s and a look for 1 to 5 s (more while EEVEE compiled its shaders): no redraw, no Stop, no orbiting, and on a long goal it looked like a hang. The dispatcher now advances such a job 50 ms at a time and gives the thread back between slices; other jobs wait until it is done, so nothing interleaves with a half-done look. The window redraws ten times a second meanwhile. Between slices a job holds names, not Blender objects (the user may delete one), and `_util.data_epoch` stops it when an undo or a file load replaced Blender's data. A look renders on Blender's own render job (F12 with "Keep User Interface") and waits for it with `WAIT`; it moves one temporary camera between views, because linking an object or switching cameras rebuilds the scene graph. The audit keeps what it measured of each object (its surface, its faces as arrays, which pairs touch or are inside each other) until that object's evaluated mesh or placement changes, and sifts face pairs on whole arrays: the same answers, 0.5 s instead of 6.6 s on that scene when little changed. Stalls over 100 ms are logged in `dispatcher.stalls`. |
| A simulation is baked a few frames per call, into a cache folder of its own | Blender's own background bake job, started from a timer, sometimes ran through every frame without simulating anything, so the blocking bake is called repeatedly on a resumable cache, about 2.5 seconds at a time. Each effect gets a unique cache folder: keyed by name alone, two files (or two open windows) with a `VFX_fire` overwrote each other's cache. |
| An effect with a shape is described, not simulated (`vfx_column`) | Asked for a fire tornado, the agent could only bake the fire preset, which gave a blob after minutes: a gas simulation makes what the physics makes, and at a resolution that bakes in a minute an 8 m column is a blur. A volume shader that works out distance from a wandering axis, a radius profile and a noise pattern turned, wound and carried upward gives the shape that was asked for at once, and it can be changed and looked at again in a second. Embers and debris are points placed from the time by geometry nodes, so nothing is cached. |
| A long job stops when its turn does | A bake polls on the main thread for minutes. When the agent that asked for it was gone (stopped, or its call cut off), the bake ran on underneath the next turn. `registry.abandon()` is called when a turn ends or is stopped; a `Pending` job from before that stops at its next step and runs its `cancel`. The CLI also gave up on any tool call that was silent for five minutes (a team, a sharp simulation): its idle timeout is switched off for the bridge. |
| A goal goes on until a fresh reviewer agrees (`/goal`, `Engine._goal_*`, `tools/goal.py`) | One turn ends when the model thinks it is done, which on a big job is long before it is. A goal chains rounds: each ends with `goal_report` (met, missing, evidence), and the next round starts from that report. A round that reports done is not believed on its word: a new agent with no memory of the work (a fresh CLI session) checks the scene against the goal's exact words, and only its done ends the goal; what it finds goes back to the conversation that did the work. Every 12 rounds the conversation starts afresh from the goal's notes; a failed round waits (1, 5, 15, 30 minutes) and starts afresh; nobody is asked anything (`ask_user` is refused); after 24 hours it stops. The goal is saved with the chat, so `/goal continue` picks it up after Blender closed. |
| Roblox Studio gets a live link: a plugin that polls a loopback server | Studio has no project folder to drop files into and cannot import a file on command, but it loads local plugins, and a plugin may use HTTP to 127.0.0.1 and build Parts, MeshParts (EditableMesh) and particle emitters. The plugin receives data only, never code. Bursts and weather go as native emitters (looping effects as a film of themselves, see below), and each open Studio window is its own target, so the agent can ask which place. Each Unix owns its port outright (no address reuse): on Windows a second process could otherwise listen on a port already in use and never be reached. |
| What Roblox has natively is sent as Parts; meshes are uploaded only with the user's yes | Roblox keeps mesh geometry only as an asset on the user's account. A MeshPart built from an in-session EditableMesh looks right in Edit mode and is a checkered box in Play and after saving. So `roblox.py` measures each mesh in world space and sends boxes, cylinders (12 sides or more), balls and triangular prisms (one or two WedgeParts) as Parts, which are exact and permanent. For the rest the `Sender` asks the user once, when the first real mesh turns up (`interact.begin_question`, never blocking the main thread); the answer can be remembered in the preferences. The same shape at another place, turn or size is sent and uploaded once (vertices travel centred, in the object's own frame, compared at size 1), and assets already used in the place are found by a key stored on the part and reused. A send that stays a preview says so in `preview_only`. |
| A surface travels whole, as a `SurfaceAppearance` built from pictures (`tools/roblox_surface.py`) | A model used to arrive as one colour, one of Roblox's stock materials and at most one 512 px colour picture. Twenty test surfaces were sent and put next to Blender renders (`tests/_roblox_look_*.png`): a panel's steel band came out white and matt, leaves cut out by a picture's alpha came out as an opaque card, a glowing picture as a white Neon slab, a picture laid on by box projection as smeared stripes, and a 32-bit linear picture two stops too dark (linear values sent as if they were sRGB). Now every socket of the Principled BSDF is read as a value, a picture found behind it (through tints, Separate Color, Invert, Math, Map Range, colour ramps), or something only nodes can make. Pictures travel in their own size up to 1024 px, once per send, in jobs of a megabyte of rows ahead of the mesh that names them, a grey map as one byte a pixel. What nodes make, and pictures laid on by anything but one set of UVs, is baked on the stand-in copy: every channel that varies, onto one fresh layout. Tried in Studio 0.742 rather than assumed: the `...MapContent` properties and `EmissiveMaskContent` take an in-memory `EditableImage`, so the preview needs no upload; without a roughness map a SurfaceAppearance is matt, so a plain polished or metal value travels as a 4 px picture of one grey; normal maps are OpenGL like Blender's and need nothing done to them; a colour map's alpha is cut at one half while the part's transparency is 0 and blended from 0.02 up, and `MeshPart.TextureID` ignores alpha altogether; light given off is strength x mask x tint x the surface's own colour, one unit being one unit of scene light, so a glowing picture's colours are put into the colour map; a part with and a part without a SurfaceAppearance that share one in-memory mesh are not both drawn, so each kind gets a mesh of its own; in-memory meshes cast no shadows. A Part cannot carry a SurfaceAppearance and keeps a stock material. Each picture becomes an image asset on the user's account when uploaded, so the upload question counts them by what they are for and the report says how many arrived, and `approximated` says what Roblox can only come close to. |
| A send is batched, and confirmed job by job | One job per object meant one round trip per object. Small items share a job up to a weight of 10,000 triangles, a heavy piece goes alone, at most six uploads per job, and Studio confirms each job before the next leaves. Conversion runs in 30 ms slices so Blender stays responsive. |
| The scene is measured after every turn (`tools/quality.py`), and only real, new problems go back to the agent | A village built in one script had walls sharing a plane (flicker), and nobody had counted the houses. The first audit compared bounding boxes and probe rays and treated every object as its own thing: on a real village it raised 80 false alarms (tree tops "floating" on their trunks, chimneys "overlapping" their roofs), the agent moved things back and forth between contradicting reports, and the check fired again after a turn that only sent the scene to Roblox. Now: things are grouped by parenting and by name (`House_0_Walls` + `House_0_Roof` = house 0) and their parts may interpenetrate freely; touching is tested triangle against triangle with a few centimetres of tolerance; an object is *hidden* when under 10% of its surface is outside the solids around it; *floating* means no chain of contact to the ground; coplanar faces that are covered (undersides on the ground) are not flicker; inside tests count crossings, so inside-out meshes still count as solid. Each problem has a key, a problem is sent back once, and a later turn brings up only what is new. |
| Roblox work is built in Roblox, as data (`roblox_build`) | A Blender effect is shaders and simulation: sent as meshes it arrives static and plain, and the agent had no way to script. The plugin now creates any instance tree from tagged JSON values (parts, emitters, beams, lights, scripts whose text the game runs on Play), reports every property Studio refuses, and plays Spin / Pulse / Flicker attributes itself so effects move in Edit mode; the same attributes are played in the game by a fixed `UnixAnimator` script. `roblox_look` screenshots the Studio window so the agent judges what it built. The plugin never executes code it is sent. Tests start the link on a private port so a real Studio cannot join them. |
| What is made here is what arrives: an effect travels as a film of itself | Asked to "make a fire tornado and get it to Roblox", the agent never opened Blender: it hand-built stock particle emitters in Studio, and when the Blender effect was sent it arrived as a generic fire preset. Neither is what the user watched being made. Now `Sender` films a looping, stationary effect (`vfx.Film`, one render per step so Blender stays alive), packs the frames into one 1024 px sheet (4 x 4 cells of 256 px for effects of 3 m and more, 8 x 8 of 128 px below; the seam is cross-faded so the loop has no jump), sends it in bands of 256 rows, and the plugin uploads it (the same yes as for meshes) and plays it with one `ParticleEmitter` as a flipbook: particles of three seconds, one every two, each fading in as the last fades out. Three things had to be solved. A flipbook cell is square and a tornado is not: a quick small look finds what the effect really covers, the camera's pixels are stretched so that it fills the cell, and the emitter's `Squash` undoes it (measured in Studio: at Squash s a particle is 1 + s times as tall and 1 / (1 + s) as wide, up to 1.5). Blender writes see-through pictures by dividing the light by the opacity before the view transform, which washes flames out to pale: the float render is read, the scene's view transform is applied to the light itself (OpenColorIO), and the opacity is raised to the brightness, so plain alpha blending adds exactly the rendered colour. And the agent's habit: `roblox_build` is refused once per message with the rule (`NATIVE_GATE`), and its description, the system prompt and the skill no longer tell it to build effects in Roblox. Without the upload the report says in so many words that Roblox holds a stand-in. |
| A rig travels as a rig: skinned meshes on one skeleton, actions as sampled poses (`tools/roblox_rig.py`) | A character deformed by an armature used to arrive frozen in its pose. What Roblox really does was tried in Studio 0.742 first. `EditableMesh` takes bones and weights (`AddBone`, `SetVertexBones`, `SetVertexBoneWeights`; four bones a vertex, weights kept as bytes) and the MeshPart made from it is skinned (`HasSkinnedMesh`), but no `Bone` instances are made for it: a mesh finds its bones by name, in its own part or in a part it is welded to, and places a vertex by `bone now x inverse of the bone's rest place in the mesh`, both absolute. So each armature becomes one invisible Part with the `Bone` hierarchy, and every piece of every mesh of the rig is welded to it (`WeldConstraint`): a mesh cut for the triangle limit is still one body. Meshes are read with their Armature modifier off (the rest shape, other modifiers applied), weights are cut to the four strongest and made to add up to 255, and an object parented to a bone rides that bone. Actions (`motion.actions_for`) are sampled a few keys per step, so IK and constraints arrive baked, and travel as `Bone.Transform` values: per key and bone a rotation in four 16-bit numbers, plus an offset only for bones that shift. They are stored in the model as base64 text (a StringValue refuses 200,000 characters) and played by fixed code: the plugin in Edit mode, and in the game a `UnixRigAnimator` script that runs on the client, because `Transform` is not sent from the server. No animation asset is needed; the model's `Animation`, `Enabled` and `AnimationSpeed` attributes steer it. Each action is also written as a `KeyframeSequence` under `AnimSaves` (checked: Roblox's own Animator, given one, puts the bones in the same pose), so the user can publish real Animation assets himself. What bones in Roblox cannot do (scale, more than four influences, shape keys, preserve volume) is listed in the report. |
| Fire and explosion are simulated (Mantaflow), baked inside the tool call | A procedural cone reads as a cone. A baked gas simulation is the only thing that looks like fire, and at 72 cells it takes about a minute. The agent CLI is started with a one-hour MCP tool timeout so a bake is not cut off. Smoke stays procedural: the simulated column spread too thin to be worth it. |
| Beginner / Advanced is a workspace switch plus hidden regions and a patched top bar (`ui/simple.py`) | A beginner needs the viewport and the island; Blender cannot remove its top bar, so its draw functions are replaced while Beginner is on. |
| Playback is a button, and starts after an effect is built | Effects are animated shaders and caches: with the timeline stopped, or in Solid view, they look frozen. |
| The agent asks before open creative builds and after a first version | Users would rather answer a question than get the wrong thing; `ask_user` options are one click on the island. Auto mode turns questions off. |
| The drag tile is a separate helper process | Blender has no API to start an operating-system drag, and Roblox Studio has no project folder to write into. |
| Binding goes through `rig_bind`, and `look` draws bones | A model re-parenting a mesh by script drops the old parents' rotation, so the mesh jumps away from correctly placed bones; and armatures do not render, so the model could not see it. The tool bakes the world transform and keeps the mesh in place; `look` adds temporary bone meshes inside a see-through model. |
| Bones are placed from measurements (`find_limbs`, `rig_chain`), not from coordinates the model reads and guesses | Guessed finger bones landed outside the fingers and the old check (3% of the whole model) could not see it. The mesh's surface distance from a root gives every limb's tip, start and centre line for any creature; the model only chooses names and joint fractions. Checks are judged against each bone's own length. |
| Weights are computed on a welded copy and copied back by position | Imported meshes are split into pieces whose border vertices only touch. Weighting each piece alone gives the two sides of a seam different weights and the surface tears when a bone moves. Welding a copy keeps the user's mesh, normals and UVs untouched. `check_rig` bends every bone and measures whether touching vertices come apart. |
| Realism is a mechanism: real photos, a traced outline, and a review pass (`tools/references.py`, `core.REVIEW_PROMPT`) | Asked for "the most realistic" pistol, the agent built one from memory out of bevelled boxes in two and a half minutes, put features on the wrong side, and stopped with "it isn't photoreal". The prompt already told it to spend the effort; that was not enough. Now `reference_search` shows it photos of the real thing, `trace_reference` gives it the true silhouette as a solid (background by border colour or alpha, largest connected piece, enclosed openings kept, outline smoothed and simplified), and when the user's words ask for realism the engine sends the agent back, up to twice, to put its render beside the photo, list the differences (including the shape across the thickness and anything on the wrong side) and fix them. None of it is specific to any object. |
| A model has to be right from every side (`profile_solid`, `look_around`, `project_reference`) | Built from a side photo, an M9 looked real from the side and was three stacked slabs from its end: every part was a flat slice with a small bevel, and nothing made the agent look from another side. Parts are now solids whose faces curve to the rim by distance from the outline (a quarter circle when the rounding fits the thickness, an oval section when it is larger; narrow stretches come out thinner), triangulated with Blender's constrained Delaunay on a lattice that is fine only near the rim. A part drawn loosely around a region of the traced photo is clipped to the subject's mask, so big parts get the true outline at the first attempt. `look_around` renders six sides into one image and the review asks for it. The projected photo is a copy with the subject's colours spread past its edge (no pale fringe), re-projection updates a layer in place, and faces turned away take the photo's average tone. |
| Animation is recorded motion where it exists, and is watched and measured (`tools/retarget.py`, `tools/motion.py`, `core.MOTION_REVIEW_PROMPT`) | Asked for walk and run cycles, the agent hand-built a rig and typed a procedural gait: the backward run leaned back with the arms up, the arms were held out like wings, a sidestep put one foot through the other, toes sank 6 cm into the floor, and it reported having seen only a few single poses. Now `motion_search`/`retarget_motion` put real recorded motion (the CMU library, Acclaim files parsed in `_mocap.py`) on any humanoid rig: bones are matched by role, each takes its counterpart's turn from rest in world space after being aimed like the counterpart's rest pose (an A-pose rig takes a T-pose recording), hips and ankles are carried over as positions scaled by leg length about the floor and the legs solved to reach them, so planted feet stay planted; the lowest points of the bound shoe meshes are kept on the floor; IK controls are driven when the rig has them. `look_motion` shows a move as a strip at one scale, `check_motion` measures it from bone matrices and linear-blend skinning of sampled points (independent of other modifiers), and a turn that changed skeleton animation without `look_motion` is sent back once. |
| The window never shows "(Not Responding)", and one copy runs at a time (`__init__._no_ghost_window`, `app_template/launcher.cs`) | Blender renders, saves and compiles shaders on the thread that answers Windows, and Windows ghosts a window after five silent seconds. Measured cause of the worst case: a second copy of the app gets an empty shader cache from the graphics driver (the first copy holds the cache file), so its first EEVEE render took 38.8 s against 1.7 s warm. Ghosting is switched off for the process (`DisableProcessWindowsGhosting`), and the launcher brings a running copy to the front instead of starting another (`--new-instance` overrides). |
| Surfaces sharing a plane are separated by the engine, not by the agent (`quality.separate`) | Told about z-fighting, the agent nudged things back and forth or reported and left it. It is geometry: for each visible pair of parallel, overlapping, same-facing faces closer than a size-dependent distance (6 mm on a house, 0.1 mm on a pistol), the smaller object is moved twice that distance: out if it is a sheet on a surface (glass, trim, a path), in otherwise. Only objects the turn made or changed are moved. Runs at the end of every turn inside its undo step, and in `check_scene`. |
| Agents work as a team on separable jobs (`tools/team.py`, `Engine._start_helper`, `McpServer.guest_config`) | Most of a turn is the model thinking, so parts built one after the other waste the wait, and one agent spreads its attention thin. `work_in_parallel` starts an agent per part with the lead's model and tools; every call still runs alone on the main thread. Each helper has its own server token, so its calls are counted for the island and the lead-only tools (splitting again, asking the user, the plan) are refused to it. |
| Studio rigs are calibrated on a grey card | An 18% grey ball rendered at 0.82 under the three-point rig: about six times too bright, so every dark object came out grey and glossy. Energies are now set so that card renders near 0.5, and a rig switches off lamps that are not part of it. |
| Tool calls run inside a window pump, never under `temp_override` (`ui/window_pump.py`) | Long sessions crashed (an access violation in python311.dll on one of Unix's socketserver threads, the main thread idle). Cause, reproduced: tools borrowed a window for their operators with `bpy.context.temp_override`, which puts a Python dict on Blender's context, so every context lookup inside an operator calls into Python. `bpy.ops` releases the GIL while the operator runs, and Blender 4.5 skips taking it for that lookup whenever any thread holds it, so with one of Unix's threads running Python at that moment (the MCP server, a CLI reader, a helper's call) two threads used Python's allocator at once and the damage killed the process later, anywhere. Under load (`tests/stress_threads.py`, the Sundial Bay scene) the old way crashed within 125 calls (twice), the new way ran 12 minutes and 1,571 calls without one. A modal operator's events carry its window, area and region and no dict, so the engine is ticked from that operator's timer; `_util.ui_context` uses the context as it is, model scripts' own `temp_override` calls are routed through `_util.window_context` by the guard, and the add-on timer ticks the engine only when no pump can run (background mode, no 3D viewport). |
| Results leave the main thread as plain data (`registry._detached`) | A tool could return a vector that reads an object's location or a bpy struct; encoded on the request thread, it read Blender memory while the main thread changed it. Results are turned into JSON values on the main thread. `UNIX_THREAD_CHECK=1` (`threadcheck.py`) reports any `bpy` use off the main thread at run time; `tests/test_stability.py` also follows every off-thread tool call by call. |
| Every Windows call is declared, on private `WinDLL` objects | Undeclared, ctypes passes and returns 32-bit ints, which cuts handles and pointers. Declarations on the shared `ctypes.windll` functions would change them for every other user in the process. |
| A fatal error leaves every thread's Python traceback (`recovery.py`, `crash_logs/`) | Blender's crash file has C frames and one Python stack; it could not say which of Unix's threads did what. `faulthandler` writes all of them; a clean exit deletes its empty log and the newest five crash logs are kept. |
| After a crash the island offers the scene and the goal back (`recovery.py`, `/recover`) | A session marker that a clean exit removes tells a crash from a normal close; a goal still marked running (a version without markers, or Blender closed mid-goal) counts too. The offer says what happened and opens a copy of the newest snapshot of that chat's scene, so no file of the user's is written, then reopens the chat and carries on with `/goal continue` from a fresh conversation told to look first. |
| Unix makes its own safety saves | Blender skips its auto-save while any modal operator runs (measured: none in 150 s with one running, one after 65 s without), and Unix always has one (the island, the window pump). On Blender's auto-save settings, when the scene changed and no tool is half-way, and a minute after a turn that changed it, a snapshot `*_autosave` is written; only the newest is kept. |
| Long chats drop old scripts | A goal runs for hours and every step kept its script: steps older than the last 60 messages keep what they did, not their input. |
| Tool inputs are stored with each step | The user can copy exactly what was run (scripts included) to reuse or report it. |
| Agent modes are prompt instructions, not separate agents | A tab adds a short instruction to the message (`island.MODES`); the same tools and skills serve every mode, so there is one code path to keep correct. |
| Skills are files loaded on demand | The system prompt stays small; detail arrives only for the stage of work in hand. |

## The standalone app

`scripts/build_app.py` produces `app/Unix/` from an installed Blender:

| Piece | How |
|---|---|
| Engine | A copy of Blender 4.5, executable renamed `unix.exe`, icon resource replaced. No other change to engine files. |
| Launcher | `Unix.exe`, compiled from `app_template/launcher.cs` with the C# compiler that ships with Windows. It starts the engine with `--app-template Unix` and no console window. |
| Application template | `app_template/Unix/` installed under `scripts/startup/bl_app_templates_system/`. Blender loads its `splash.png`, `startup.blend` and `userpref.blend`; its `__init__.py` enables the add-on, replaces the splash menu with the mode chooser and adds the brand and mode switch to the top bar. |
| Add-on | Copied to `scripts/addons_core/unix`. |
| Settings | A `portable` folder beside the executable makes Blender keep all user data inside the app folder. |
| Start-up file and preferences | Built by `scripts/app_setup.py` running inside the app: it makes the Zen workspace (one clean viewport, shown as Beginner) and the Studio workspace (shown as Advanced), applies the theme and saves both files into the template. |

With a template active, Blender takes the theme, add-on list and keymaps from the template's `userpref.blend`, which is why the build ships one.

## Adding a tool

```python
# unix/tools/<module>.py
from .registry import tool, ToolError, ToolOutput

@tool("my_tool", "What it does and when to use it.",
      {"name": {"type": "string", "description": "..."}}, ["name"],
      mutates=True, label="Did the thing")
def my_tool(name: str):
    ...
    return {"ok": True}          # or ToolOutput(data, images=[path])
```

Import the module in `tools/__init__.py:load_all`. Raise `ToolError` for failures the model can act on. Call `_turn.mark_mutation()` before changing the scene. Add a case to `tests/test_tools.py`.

A tool that can hold the main thread for more than a few hundred milliseconds on a big scene is written as a generator: `yield` where it may pause (between objects, between renders), `yield WAIT` while Blender works on its own thread, and `return` the result. Do not keep Blender objects in variables across a `yield` (keep names and look them up again), and in a `finally` check `_util.data_epoch()` before touching what was held. `tests/test_responsiveness.py` checks the slices.

## Known limits

- A script deadline stops Python loops, but not a single long C call inside Blender (a heavy boolean or bake).
- A `run_python` script cannot be sliced: the window is frozen while it runs (the reply gives its `seconds` and the prompt asks for light scripts on big scenes). The same holds for the safety snapshot taken before a turn's first change (saving a copy of the file, about half a second on a big scene), Blender's own undo steps, an import, an export and `look_motion` (which still renders frame by frame in one go). A look still holds the thread for a few hundred milliseconds while it sets up and starts each render: the scene graph is rebuilt once for its camera.
- A script's `temp_override` of members other than the window, screen, area and region (`selected_objects=`), and the island's own buttons, still make a real override: the crash's mechanism is still possible there while other threads are busy, only far rarer (a few context lookups per click instead of per operator in every tool). Blender's own fix would be to take the GIL in `BPY_context_member_get` whenever this thread does not hold it.
- The script guard is a denylist, not a sandbox. With it off, scripts have full Python.
- The chat is a sidebar panel of wrapped labels. Stock Blender has no rich-text or multi-line input widget.
- Restoring a snapshot starts a fresh model conversation: the CLI session cannot be rewound, so Unix no longer remembers the turns that were removed.
- The viewport lock is a modal operator; it ends on the first input event after a run finishes.
- Roblox rigs: bones do not scale, a vertex follows four bones at most, shape keys do not animate, and a rig's animation is played by a script on each client (the server does not see the pose). Whether a skinned mesh keeps its skin through the upload to the user's account, and how it plays in a running game, has not been tried (nothing is uploaded or play-tested by the tests); a piece that comes back unskinned is reported. Roblox surfaces: pictures are sent at up to 1024 px (Roblox's limit); a native Part keeps a stock material because only a MeshPart can carry a SurfaceAppearance; subsurface, coat, sheen and anisotropy have no counterpart and are dropped; glass is Roblox's Glass at half transparency, without refraction; a glowing surface does not light what is around it; mirrored texture repeats arrive as plain repeats. In a preview (nothing uploaded) the meshes cast no shadow and fine patterns in a picture shimmer when seen small; both were seen in Studio 0.742 with in-memory meshes and pictures only. Whether the pictures look the same once they are image assets (after the upload, in Play and after reopening the place) has not been tried: nothing is uploaded by the tests. A mesh is permanent only once uploaded to the user's account; the upload path (`AssetService:CreateAssetAsync` from the plugin) needs the user's consent each install.
- Without the Studio plugin, Roblox gets a file imported by hand (File > Import 3D or the drag tile).
- Unreal: rigged meshes arrive as static meshes in their current pose (no skeleton or animation yet), the world (sky, background light) is not sent, geometry instanced by geometry nodes (not objects) is skipped, round area lights become rect lights, glass is a quarter-opaque translucent material without refraction, a turned Mapping node arrives unturned, and Unreal's auto exposure decides how bright the level looks. The link needs UE 5 (editor subsystems); without remote execution the FBX lands in Content/Unix and the link is switched on for the next start.
- Engine discovery reads Windows process command lines and per-user settings files; it is Windows only.
- No image-to-mesh or video generation, by the owner's decision (no API keys, no local models). Products that do better on detailed real objects call trained mesh generators; Unix models from a traced photo instead, which gives a correct outline, rounded parts and the real surface, not generated-mesh detail. Image to 3D is done by modelling against a generated reference sheet, which suits man-made objects and only approximates organic ones.
- Switching between Claude and Codex mid-chat starts a fresh model conversation; the two CLIs cannot share one.
- The Codex runner reports no cost figure, and an AI image takes about a minute.
